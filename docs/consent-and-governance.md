# Consent And Governance Pack

## Purpose

This document defines consent, privacy, ethics, and governance expectations for a controlled MindMap Care pilot.

It must be adapted to the selected institution, country, site, and approval pathway before any real screening records are captured.

## Consent Principles

- Consent must be obtained before digital screening.
- Clients must understand that MindMap Care is screening and triage support, not diagnosis.
- Refusal must not block routine care.
- Consent language must be understandable in the client's preferred language where feasible.
- Consent status, timestamp, and consent wording version should be auditable.

## Minimum Consent Explanation

The approved local consent script should explain:

- why screening is being offered
- what information will be collected
- who can see the information
- how risk outputs are used by human reviewers
- that the tool does not diagnose conditions
- what happens for urgent or high-risk outputs
- how long data may be retained
- who to contact with questions or concerns
- that participation can be declined according to local policy

## Consent Records

Minimum fields for live use:

- consent confirmed
- consent date and time
- consent wording version
- screener ID
- site ID
- language used
- client or guardian consent pathway where applicable
- reason screening did not proceed if consent declined

## Governance Roles

| Role | Responsibility |
| --- | --- |
| Clinical owner | Intended use, escalation pathways, clinical safety, pause decisions |
| Data protection owner | consent, access, retention, exports, privacy incidents |
| Technical owner | deployment, security controls, backups, audit logs, rollback |
| Validation owner | evaluation plan, evidence summaries, explanation review, subgroup analysis |
| Programme lead | site workflow, staffing, training, monitoring, partner communication |

## Approval Checklist

Before pilot launch:

- [ ] institutional approval pathway identified
- [ ] ethics review need assessed
- [ ] data protection review completed
- [ ] consent wording approved
- [ ] retention schedule approved
- [ ] data access roles approved
- [ ] incident reporting pathway approved
- [ ] local referral and urgent escalation pathways approved
- [ ] support and pause authority assigned

## Data Retention

Retention must be site-approved before launch.

Draft expectations:

| Record type | Draft rule |
| --- | --- |
| Screening record | retain only as long as needed for pilot care coordination and evaluation |
| Audit log | retain according to governance and accountability requirements |
| Draft report export | short retention, access-limited, removed after use |
| Training records | retain through pilot closeout |
| Incident reports | retain through governance and regulatory review period |
| Backups | encrypted and deleted according to approved backup schedule |

## Access Governance

- All users must have named accounts.
- Shared accounts are not acceptable for pilot use.
- Access should be reviewed before launch, monthly during pilot, and after staff changes.
- Admin access should be limited to named owners.
- Support access should be time-bound and logged.

## Data Sharing

No identifiable pilot data should be shared outside the approved pilot team unless:

- the purpose is documented
- legal or ethics approval allows it
- the data protection owner approves it
- the minimum necessary data is shared
- transfer and storage controls are defined

## Governance Review Cadence

| Review moment | Minimum output |
| --- | --- |
| Before launch | approval record, open-risk list, go/no-go decision |
| Weekly during pilot | incidents, safety concerns, downtime, follow-up gaps |
| Monthly during pilot | access review, risk register update, monitoring summary |
| After incident | containment action, notification decision, prevention plan |
| End of pilot | evidence summary, lessons, scale/stop/redesign recommendation |

## Open Local Decisions

- selected legal basis for data processing
- consent process for minors or vulnerable adults
- local language requirements
- retention period by record type
- incident notification obligations
- data export permissions
- whether evaluation is operational review, research, or both
